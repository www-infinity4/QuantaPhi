# Complete account recovery

The credential-only recovery repaired in ec34601 still failed when TV-Database's real authentication loader ran. Its `currentUser()` needs both `starquest_session` and the selected record inside `starquest_users`. Without that record it clears the session. Control Phi then uses its Guest wallet, and the StarQuest cloud bridge cannot bootstrap the signed-in account. Tests that only called the fallback bearer request did not detect this failure.

The bridge now transfers the selected account's minimal bootstrap record, its existing credential, and its session together. It imports that record before the session reaches the authentication loader, merges only a missing selected account into an existing user dictionary, and never overwrites an existing account's history or password proof. Other account records and password text are excluded. Balances and full history remain backed by the existing cloud service; the account cache retains current summary balances while it connects.

An existing credential without its account record still requests recovery. The gateway returns directly only when it can supply both; otherwise it checks the original GitHub storage origin. A single established credential may select its matching saved or backup account record when the old session was cleared. Multiple accounts are never chosen arbitrarily. The once-per-session recovery marker advances to v4 so earlier failed recovery attempts do not prevent this correction.

`test/account-recovery-flow.test.cjs` executes the real authentication and cloud-bridge code from the public TV-Database source snapshots in `test/fixtures/`. It verifies selected-account recovery, credential/password-proof forwarding, cloud state application, an account restored from its backup, preserved local history, and the gateway fallback. Running the account tests with the previous client reproduces the signed-out failure. All service replies in these tests are fixtures: they do not establish the account state on Kris's phone.
