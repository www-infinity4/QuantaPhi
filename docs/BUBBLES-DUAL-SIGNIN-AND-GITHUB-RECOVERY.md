# Bubbles: persistent two-provider access, complete GitHub mirror, and device recovery

## User-requested destination
Before Bubbles opens chat, require separate **GitHub** and **Cloudflare** account authorization screens with the permissions each provider actually grants. Show existing durable, non-expired authorizations on later visits instead of asking for them every time. After both are verified, create or select exactly one user-owned **private** GitHub mirror, verify the first real commit, and then unlock chat. There must be a clear progress/retry state, not a spinning screen.

The wallet belongs to QuantaPhi's existing Cloudflare ledger, **not** an arbitrary GitHub JSON file. A new phone can use both verified provider accounts to request recovery of that original wallet identity, with a device-key challenge and owner-approved grant. Repository files are historical evidence, not funds. Neither GitHub identity nor balance strings alone may mint, transfer, merge or reassign coins.

## Stages and gates

1. **Real Cloudflare OAuth connector (this PR: source only).** Cloudflare OAuth authorization-code + PKCE; server-held OAuth client secret; requested `user-details.read`, `memberships.read`, `workers-scripts.admin`, `d1.read`, `d1.write`, `page.write`. GitHub App OAuth exists already. Both use the same per-wallet Durable Object, verified external subject, encrypted credential vault and refresh/revoke lifecycle. **Not yet live**: account-level OAuth client registration and secret installation remain unverified.
   - Cloudflare client callback: `https://quantaphi.org/api/bubbles/connections/cloudflare/callback`.
   - GitHub callback: `https://quantaphi.org/api/bubbles/connections/github/callback`.
   - Install **Cloudflare OAuth client** secrets as `CLOUDFLARE_CLIENT_ID` and `CLOUDFLARE_CLIENT_SECRET` server-side in `bubbles-connections`.
   - This user's connected Cloudflare integration could enumerate OAuth scopes but **returned HTTP 403 with OAuth Client Read denied** for `GET /accounts/{account_id}/oauth_clients`. Its current authorization cannot create or inspect an OAuth client. Do not claim client setup succeeded. Cloudflare OAuth client is a separate app from the existing path-specific Access owner recovery form.
   - Before public rollout Cloudflare requires an OAuth **public client** and verified publisher domain. It is an account-owned, administrator-approved publication; do not issue third-party permissions using the platform owner's token.

2. **Two-provider pre-chat gate.** Verify existing StarQuest wallet and separately validate persistent `github` + `cloudflare` records with permitted actions server-side; send each user through actual OAuth consent only if missing/expired/revoked. Show both cards with one-click sign-in and readable errors. Do not enable a hard block on production chat while Cloudflare OAuth remains unconfigured; test on canary first. Cloudflare Access recovery sign-in is **not** Cloudflare API permission.
3. **Automatic private repo provisioning.** After provider consent, let the user explicitly approve one private repo *at setup*, then automatically create it under the authorized GitHub identity, select it under a per-wallet namespace, verify actual installation write permission, and record repo ID and account mapping in Cloudflare. No API token/user credential in repo files. Do not fall back to the platform GitHub credentials or create a public repository.
4. **Full verified exports.** Add versioned, paginated, canonical JSON mirrors for StarCoins; Quants; Infinity; Music Quants; all available mints, credits, debits, shares, searches and Robot Brain job receipts where authorized. A 500-row snapshot is **not** full history. Use signed manifests (Ed25519 or equivalent) + monotonically increasing watermarks and hash-chain continuity. When sources omit search history, return an explicit coverage gap; do not invent missing events. Include idempotency, bounded retry, checkpoint and verified commit receipts.
5. **Ongoing reconciliation.** Use a Cloudflare outbox/scheduler or queue to compare source D1 event sequences with private GitHub commits after changes, on retry, and periodically. Surface `verified`, `lagging`, `conflict`, `missing` states; do not silently overwrite tampered records. Cloudflare remains authoritative and comparison hashes live in separately controlled durable storage. GitHub history can be rewritten, so no honest system can literally guarantee never losing all history without another independent archive.
6. **New phone/device recovery.** Reauthorize providers, verify prior Cloudflare-wallet↔GitHub external subject binding against server-side durable record, challenge the new Android Keystore device key, rate-limit and audit recovery, issue short-lived single-use server grant and bind the existing account. Never transfer/mint coin balances to a new account; restore authenticated view of the original ledger and read-only GitHub archive. Persist verified session in Android Keystore; reauth only on revoked credentials or new hardware.
7. **Phone-first validation.** Run lost-Chrome-cookies, new-phone, revoked-GitHub-permissions, tampered-repo, concurrent-redemption, missing-batch, partial-backup and provider-outage tests on Android + live Cloudflare before advertising protection.

## Stage 1 scope and safety

Stage 1 adds a *configuration-gated* Cloudflare adapter with a real `dash.cloudflare.com/oauth2/auth` user consent URL, signed PKCE state bound to a verified StarQuest session, token exchange against `/oauth2/token`, identity subject lookup at `/oauth2/userinfo`, refresh and revoke. The existing tenant-isolated vault does not return any provider token to chat. The adapter checks granted scopes before advertising account/build/read actions.

Cloudflare project-management permission must be granted **by each account owner on Cloudflare's native consent screen**. It cannot be preapproved by Bubbles. "All permissions prefilled" can mean Bubbles requests its documented scopes as required on the consent page, but the user still gets a genuine accept/deny choice.

Stage 1 is not completion of backup/recovery. No GitHub wallet repo has been generated by this PR and no ledger entries are modified.
