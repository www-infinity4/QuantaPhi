# Continuity Builder: actionable packet executor contract (#1321)

This source-only module does not itself call GitHub, Cloudflare or Bubbles and must not claim to run autonomous jobs. The authenticated runner must consume and persist the packet contract before production use.

`continuity/packet-runner-adapter.mjs` is an independently tested adapter seam. It
requires an active, fenced D1 coordinator claim and an opaque owner-scope hash,
reads candidate history only for a changed SHA-1/SHA-256 source version, and
persists packet receipts and blockers to D1. Its candidate reader and action
executor are injected capabilities; the seam itself has no GitHub credentials
and does not prove that an action ran.

## Resume without a history-reading loop
Read latest approved work/unfinished/INDEX.md once and fetch actual GitHub state for the chosen candidate; use a lastScannedVersion checkpoint to skip unchanged history, and never re-read every PR each hour.
Every packet carries repo, issue, exact 40-char headSha, one nextAction, nextSourcePath, priority, state, independently verified lease (if any), exact CI/review state and last result.
Selection considers up to 5 actionable candidates, skips duplicate issue/head, already attempted done packets, unchanged known blockers and genuinely active foreign leases. Safety holds prohibit merge.
Run at least one genuinely authorized test/write/review or merge action before stopping for source-only status if a safe candidate exists. Blocked candidate gets one reason and immediate rotation to next candidate.
Each provider-confirmed mutation needs a real URL or SHA; approved review and green exact-head CI precede merge. Deployment and live browsing remain separate confirmations.
Do not invent a lease, use another business's credentials, modify wallet/auth/Cloudflare private services without permission or fabricate a merge merely to avoid zero activity.

The integration acceptance remains: wire through that existing authenticated route, then verify a real eligible action/PR through exact-head CI, independent review and guarded merge; a resumed run must skip the unchanged checkpoint without rereading history or duplicating a write. Preserve owner grants, wallet and security gates. The seam's synthetic adapter tests are not that production acceptance.

## Color handoffs are observable data-processing states

The color names are compatibility labels for states/functions in one programmer-directed system, not proof of autonomous individual bots. The programmer specifies the requested output; authorized software implements it. Each state and any real transition stays attached to the same ticket/job, repository, branch, source SHA and verified lease/fence. Red is the bounded connected context/data graph, including relevant searchable source and destination sectors; it is not a whole-world or whole-repository rescan. Red is also the receiving context for accepted incoming records. For a known scoped code repair, irrelevant handoff states can be skipped.

Yellow searches/extracts/filters within Red and records the sector, query, immutable candidate/source IDs, source URL and content hash. It can continue discovering while another candidate is transported. Orange uses programmer intent, Red context, Yellow evidence, provenance and confidence to resolve what an ambiguous candidate means and select the precise destination. For example, “Sandy Beach” might refer to a place, person, post or video; refine Yellow's search within a strict budget if the evidence does not resolve it. Orange's decision is not a write authorization or an extra model call on every known repair. Freeze the selected Red source version for that item; a retarget requires rechecking the fence and permissions.

Blue is actual lawful, authorized, schema-validated, idempotent transport/import/export to the addressed destination. Distinguish `blue.import_requested`, `blue.write_confirmed`, and `blocked`; only an existing adapter's provider-backed write receipt proves transport. Red then checks authorization, schema/types, provenance, duplicates, owner partition, conflicts, source version/fence and destination readback. Record successful assimilation as `red.import_accepted` then `purple.integrated` (`Red ⊕ accepted Blue`); reject or quarantine mismatches. Purple is this verified destination assimilation state, not necessarily an independent reviewer/bot. It cannot replace independent code/security review, CI or release gates.

Green denotes the visible combined activity of Yellow discovery/extraction and Blue transport as a requested output is assembled, and may overlap both. It is not necessarily a separate actor/model call, a completed code change or a production artifact. Any speculative artifact remains staged; a real product exists only after the authorized builder actually writes it and applicable tests pass. Use `green.build_committed` only for a provider-confirmed commit, not for the emergent Green process itself. Pink testing and Black release-evidence functions can remain named gates, but no separate bot execution is implied without receipts. Keep independent review, security, merge and deployment receipts distinct.

For example (design only), a programmer may request permitted content from an X/Twitter sector matching “Sandy Beach” for a Quick Card. Yellow identifies sourced candidates, Orange resolves the intended subject and destination, Blue transfers only permitted validated data, Yellow may keep searching while transport proceeds (the combined Green activity), and Purple verifies the destination safely assimilated the payload. This example does not authorize scraping or media embedding and is not evidence that a card was made.

Any emitted transition receipt is provider-backed and scoped to the same job. Its verified fields may include `jobId`, state/compatibility role, `inputRef`, `sourceSha`, applicable `selectedRecordIds`, destination, decision reason, adapter, output reference, operation status, timestamp and next state. Distinguish `model_reasoned`, `tool_executed` and `data_written`; omit unverified fields. A read-only observation is not a search, import, write or build receipt. If a state is not used, report skipped/irrelevant rather than inventing activity.

## Bounded streaming and feedback

These states form overlapping, feedback-controlled loops, not a mandatory one-color queue. Red publishes a bounded authoritative context snapshot and stable source-version anchor. Yellow may continue discovering/filtering other candidates while an already-selected item moves through Blue; Orange pins that item to the exact Red version and destination. Blue transport and the combined Green activity may overlap on independent items under the same job-scoped lease/fence and explicit concurrency budget. A changed target requires revalidating authorization, schema, idempotency and fence. Purple's verified accepted state updates Red's next snapshot. No state name alone proves a tool ran or an artifact was built.

“Enough entropy to escape the run” means a bounded, observable completion/rotation decision, not thermodynamic entropy or an infinite loop. For each item, track evidence such as distinct verified source count, new eligible candidates, unresolved contradictions, target resolution, authorized write receipt, destination readback match, tests passed, iteration count and configured maximum. Provider/model prose cannot set these signals to success. Stop that item as `accepted` only when target, authorization, required persistence/readback and applicable tests are evidenced; otherwise mark `blocked` on a genuine blocker or `deferred` when the budget/iteration ceiling is reached. Rotate immediately when the same source/version/destination or blocker signature repeats, marginal verified evidence gain is zero, a safety/permission gate fails, or the configured candidate/time/credit/retry budget is exhausted. Dedupe transport/build work by immutable source ID + content/version hash + destination so an unchanged run resumes without repeating reads or writes. Keep concurrent work bounded and checkpoint each outcome under its active fence; uncertain write outcomes require reconciliation/readback before retry.

### Iteration receipts and future UI

If a future authenticated runner displays a Green sequence of dots, each dot represents exactly one persisted, real operation/iteration receipt—not decoration, an estimated count, or proof of success. Reopening a dot shows that receipt's actual input/pull/filter/decision/output/push, status (including failure or blocked), timestamp, source references, criteria and measured before/after counts, rejection reasons, target, adapter, immutable receipt/output reference and next action. Counts must come from the provider receipt; rejection reasons must be non-overlapping or explicitly marked as overlapping. A dot's color does not mean success.

Receipts should be deduplicable and resumable using `eventId`, shared `jobId`, lease/fence, monotonic `sequence`, `sourceVersion`, `phase`, `colorsActive`, `operationKind`, `inputRefs`, `outputRefs`, criteria, counts, rejection reasons, selection reason, target, adapter, receipt URI/SHA, status, timestamp and `nextAction`. Record only verified fields. Derive any future expanded-dot view from these persisted receipts and dedupe by event ID plus source-version/destination; do not synthesize dots from plans, model prose, candidate totals or transient UI state. Any hypothetical figures (including 550 found / 525 filtered) are examples, not provider results. Interactive UI is follow-on work after authenticated persisted receipts exist; this PR adds no dot UI or event writer. A future UI must use accessible text labels and touch targets of at least 44px.

This ontology and the overlapping loops are a design contract only in this PR. No Yellow discovery overlapped Blue transport, no Orange ambiguity/target decision or live budget counter was exercised, and no Green output was built. The adapter tests exercise synthetic injected capabilities and do not provide the authenticated candidate reader, importer, Red acceptance/readback or production runner. In this PR the evidenced work remains source/document editing and local Node tests only: no Blue write, Red acceptance/readback, Purple assimilation, production card build, merge or deployment occurred.
